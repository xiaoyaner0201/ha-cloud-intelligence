# Cloud Intelligence ローカル Home Assistant 統合

[English](README.md) | [简体中文](README.zh-CN.md) | [日本語](README.ja.md)

**ローカル統合のベータ版です。** 非公式の独立した
コミュニティプロジェクトで、最初の対応機種は Wilo HiMulti-1 WiFi のみです。
Android の Cloud Intelligence（云智能）で取得した、ご自身の機器の LAN 認証情報を
インポートします。アカウントログインやクラウド機器検索ではありません。Google ログイン、
認証情報の抽出、自動更新は実装していません。アプリにエクスポート機能があるとは限りません。

## 機能とインストール

- Wilo のネイティブ機器と12個の読み取り専用状態：水圧、水温、目標圧力、モード、
  故障コード、故障、電源許可、モーター運転、始動圧力比、ソフトウェア版、目標/実際の回転数。
- 機器ごとに標準 HA 設定エントリーを作成し、複数機器、認証情報の保存、再起動後の復元、
  再インポート、アドレスの再設定に対応します。既定では運転制御を有効にしません。
- 更新は標準120秒、最短60秒。各通信の総予算は10秒で、12個の実際の状態を受信すると直ちに終了。
  常時起動アプリ、クラウド接続、非公開ヘルパー、常駐リスナーは使用しません。
- HA 2026.9.1 / Python 3.14.6 で検証済みです。オフラインのライフサイクルテストは合成通信を使い、
  別途、実機で初回設定、12個の状態、自動ポーリング、HA プロセスの完全再起動を確認しました。
  再起動後も同じ設定エントリーと機器・エンティティ ID が保持され、認証情報を再入力せず新しい状態を受信しました。
- 安定エンドポイントと制御修正を導入した最終約10時間の観察では、ポーリング失敗により
  エンティティが unavailable になることはありませんでした。より長期のファームウェア安定性、
  ブラウザーの表示確認、他機種は未検証です。

コードの `custom_components/cloud_intelligence` 全体（`_core`、`translations` を含む）を
HA 設定ディレクトリの `custom_components` 内にコピーして再起動します。
**設定 → デバイスとサービス → 統合を追加 → Cloud Intelligence (Local)** で次を入力してください。

| 項目 | 内容 |
| --- | --- |
| Name | 表示名。既定は Wilo HiMulti-1 WiFi |
| Host | HA から到達できる機器のプライベート LAN IPv4。公開 IP や DNS 名は不可 |
| `productKey` | 対応キーは `a15zaTr5sp1` のみ |
| `deviceName` | 認証情報内の固定 ALCS 識別子。表示名ではありません |
| `accessKey`、`accessToken` | ご自身の機器のローカル認証情報。機密情報です |

`iotId` やクラウドパスワードは不要です。機器の UDP 5683 との双方向通信が必要で、
マルチキャスト検索はしません。初回追加には機器の識別、認証、12状態の検証が必要です。
ACK や更新要求のエコーだけでは成功になりません。各回に固定の `refresh=1` 状態レポート要求を
一度だけ送信します。電源・モード・圧力設定は変えませんが、純粋な GET や受動監視ではありません。
未対応機種への能動的なレポート要求は拒否し、TSL の書き込み属性から制御を有効にしません。

### HACS でのインストール

HACS の **カスタムリポジトリ** で
`https://github.com/xiaoyaner0201/ha-cloud-intelligence` を **Integration** として追加し、
ダウンロード後に HA を再起動してください。その後 **Cloud Intelligence (Local)** を追加します。
カスタムリポジトリとして提供するベータ版であり、HACS 標準カタログには掲載されていません。

手動インストール用 ZIP は [GitHub Releases](https://github.com/xiaoyaner0201/ha-cloud-intelligence/releases)
から取得できます。内容は `custom_components/cloud_intelligence/...` なので、HA 設定ディレクトリに
展開して `custom_components/cloud_intelligence/manifest.json` が存在する状態にしてください。
HACS はリポジトリのソースを使用し、この手動 ZIP は使用しません。
リポジトリ直下の `cloud_intelligence` パッケージはコピーしないでください。

## 実験的な電源許可制御（既定無効・実機検証済み）

エントリーのオプション `enable_power_control` を明示的に true にすると標準 HA switch を追加します。
既定は false、変更時は既存エントリーを reload。12個の読み取り専用状態と機器・設定 ID は維持し、
新しいスイッチは独立した control-role ID を使用します。追加されたエンティティへの
`switch.turn_off` で電源許可を停止し、`switch.turn_on` で復元します。`switch` はモーター運転 `run` ではありません。
補水連動用の呼び出しインターフェイスであり、自動補水ガードや安全認証された非常停止ではありません。

HA coordinator のみ、既に進行中の読み取りポーリングを待てますが、別の制御は待ちません。
待機前に制御枠を確保し、新規ポーリングの割り込みを拒否します。待機と一度だけの新鮮な
事前読み取り・送信・検証を含むサービス総予算は10秒（呼び出し元の12秒 I/O 枠内）です。
失敗したポーリングの値は制御に流用しません。キャンセル・アンロード時は枠を解放し、
汎用キュー、新クライアント、自動再送は追加しません。core client の並行操作は従来どおり即時拒否します。

制御スイッチへの `homeassistant.update_entity` は要求更新のクールダウンを使わず、実際の読み取り完了を待ちます。
更新中・失敗時は unavailable、有効な電源許可を含まないレポートは unknown のままです。キャッシュされた on を
復元判断の根拠にはできません。並行する明示更新は unavailable として拒否し、古い状態を黙って返しません。

厳密な bool のみ受け付けます。同じ認証済み Observe セッションで完全かつ有効な新しい状態を取得し、
`switch/presSet/mode/propor/tarSpeed` を記録。既に目標状態なら no-op、それ以外は固定の
`{"switch":0}` または `{"switch":1}` を一度だけ送信します。同じ排他ゲート・安定ポート・総予算10秒内で、
送信後に再認証して新しい Observe token/key 検証ウィンドウを作り、12状態を再取得して目標と他の4設定の不変を確認します。
送信前の値、旧セッション通知、ACK/set成功コードは証拠になりません。測定値・実回転数の変化は許容します。
時刻はローカル受信時刻のみです。ALCS opt 1 に MAC/リプレイ保護はなく、新ウィンドウも全ての悪意ある
リプレイや機器内部の古いキャッシュを排除する保証ではありません。

送信試行後のタイムアウト・キャンセル・応答損失・検証失敗は outcome unknown とし、自動再送も楽観更新もしません。
HA 状態は正常な読み取りまで利用不可。復旧ガードはまず読み取りで判断し、盲目的な再送・復元を避けてください。
無効時は直接/古いエンティティ呼び出しを拒否し、HA 標準サービスはアンロード済みターゲットをスキップして書き込みません。
圧力・モード・回転数・任意プロパティの設定、クラウド fallback、常駐プロセスは追加しません。

HiMulti-1 実機では、まず隔離環境で約1.2秒の有界な off→on サイクルを実施しました。
完全な読み戻しで他の書き込み可能設定が不変であることを確認し、不確定結果・再試行はありませんでした。
次に実際の HA 2026.9.1 で、別途保守する HA ネイティブの補水連動自動化（本リポジトリには含まれません）
による5シナリオを確認しました。通常2サイクル（洗浄終了後約0.54/0.58秒で off、約120秒後に復元）、
最初から off なら維持、手動 off による自動復元の取消、停止期間中の HA 再起動後の安全な復元です。
その後の日常使用9サイクルでは、終了後0.505–0.627秒で許可を停止し、119.2–120.0秒後に復元しました。
全書き込みが内蔵の読み戻し検証を通過し、目標圧力・モード・始動圧力比・目標回転数は不変で、不確定結果はありませんでした。

以前の本番検証では120秒後の復元がポーリングと衝突し、`Local operation already in progress` で失敗して
安全な手動復元が必要でした。有界なポーリング待機、制御枠の事前確保、デバウンス外の新鮮な更新、
絶対10秒期限の修正後、本番ログの同種エラーは0件です。確認できた範囲の結果であり、ファームウェアの根本原因や
全ての損失・キャンセル・長期条件を検証したものではありません。[実機検証](docs/verification.md#live-acceptance)を参照してください。

## 安定エンドポイント（実機検証済み）

同一クライアントは最初に OS が割り当てた認証/Observe 用 UDP 送信元ポートを記憶し、成功・失敗・
タイムアウト・キャンセル後も再バインドします。毎回、独立した一時ソケットで機器を厳密に識別した後、
認証・購読・固定レポート要求を一度行い、全ソケットを閉じます。同一クライアントの並行読み取りは
待機せず直ちに失敗し、受け付けた読み取りの総予算は従来どおり10秒です。ポート競合時は明示的に失敗し、
別ポートへの切り替えや追加再試行はしません。ポート設定、共有ソケット、再利用オプション、常駐リスナー、
ハートビートは追加しません。通信間にポートは予約されず、設定・診断・repr に保存・表示しません。
新しいクライアントやプロセスは別のポートを選択できます。

限定的な HiMulti-1 実機比較では、同一の `LocalClient` で120秒ごとに読み取り、約2時間で連続61/61回成功しました。
毎回12状態を全て取得し、認証/Observe の送信元ポートは不変、受信時刻は進み続けました。その後も本番設置の一部として稼働し、
最終約10時間の観察ではポーリング失敗によりエンティティが unavailable になることはありませんでした。

これは観察範囲内の動作確認であり、以前の受信停止のファームウェア原因を特定したものではありません。
ローカルの close は遠隔セッションや監視登録の解除を意味せず、同一エンドポイントでの再認証も清掃・復旧を保証しません。
Observe=1/RST による解除や機器障害の根本修正は主張せず、より長期のファームウェア安定性は引き続き観察が必要です。

## 保護・復旧・制限

認証情報は HA の標準設定エントリーに保存され、**本統合では暗号化しません**。HA の設定、
バックアップ、アクセス権を保護し、認証情報、機器識別子、アドレス、パケットを Issue に貼らないでください。
保存しても有効期限は延長されません。認証が無効になったら HA の再認証から、同じ `productKey` と
`deviceName` の認証情報を再インポートします。別の機器は拒否されます。アドレス変更にはエントリーの
**再設定** を使用し、認証情報も再入力してください。更新間隔はオプションで変更できます。

初回の接続失敗は HA 標準の再試行、更新失敗は利用不可になります。後続の部分レポートで欠けた状態は
不明となり、ゼロや以前の値で補いません。電源許可とモーター運転、LAN 到達性とクラウド接続は別です。
`locally_received_at` は HA ホストの実際の受信時刻で、機器のタイムスタンプではありません。
対応する ALCS opt 1 はパケット MAC やリプレイ保護を提供しないため、信頼できる LAN のみで使用してください。

既定の120秒ポーリングではモーターが停止する秒単位の瞬間は分かりません。安全規格に基づく停止ではありません。
長期運用、ファームウェア差異、認証情報の失効、実機の損失/キャンセル復旧、ブラウザー表示は引き続き検証が必要です。
完全なアカウント検索、Google ログイン、自動更新、他機種、明示的な電源許可以外の運転制御は本候補版の範囲外です。
基本 UI は en、zh-Hans、zh-Hant、ja と英語へのフォールバックを備えますが、全言語対応ではありません。

開発用の[固定依存](requirements-dev.txt)をインストール後、`make check` で純 Python コアと
実際の HA 2026.9.1 コンテナーのオフラインテスト（2 GiB / 2 CPU）を実行します。
個別実行は `make check-core` / `make check-ha`。詳細は[英語版](README.md)、
[要件](docs/requirements.md)、[検証](docs/verification.md)、[セキュリティ](SECURITY.md)を参照。
